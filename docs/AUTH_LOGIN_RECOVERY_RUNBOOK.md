# CrediSafe Auth: login, registration and recovery runbook

This change fixes client-side flow issues, callback redirect safety, session
cookie preservation, production demo-mode bypass, and password recovery.
It cannot repair an externally misconfigured Supabase project without access
to that project's Authentication settings.

## Runtime configuration

Vercel project `credi-safe` should have these values in Production and Preview:
- `NEXT_PUBLIC_SUPABASE_URL`: the HTTPS project URL from Supabase.
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`: the publishable/anon key ONLY.
  Never use a Supabase `service_role` or `sb_secret_...` value here.
- `NEXT_PUBLIC_SITE_URL=https://credi-safe.vercel.app`: canonical website origin.
- Existing Vision-service variables are unrelated to user authentication.

The code checks the URL and rejects known server-only key formats. If Supabase
settings are missing/malformed in production, the protected app now fails
closed with an actionable error instead of silently opening local demo data.

## Supabase Dashboard checks (required for email links)

Open Supabase Dashboard → Authentication → URL Configuration:
1. Set **Site URL** to `https://credi-safe.vercel.app`.
2. Add `https://credi-safe.vercel.app/auth/callback` to Redirect URLs.
3. Add `https://credi-safe.vercel.app/auth/confirm` only if using a custom
   email template with `token_hash` / `type` links.
4. For local development only, add `http://localhost:3000/auth/callback`.
5. Do not add broad wildcard domains unless they are required for a controlled
   preview workflow. The application intentionally sends emails to the
   canonical production origin when `NEXT_PUBLIC_SITE_URL` is set.
6. In Authentication → Providers → Email, confirm email/password sign-in and
   the desired email-confirmation policy.
7. If confirmations or resets are not arriving, check Supabase Auth logs,
   SMTP/provider delivery, sender verification and rate limits. Supabase's
   built-in email sender is rate-limited; configure custom SMTP for production.
8. Review the confirmation/reset email templates. The default confirmation
   URL should preserve the RedirectTo target. If using a custom token-hash
   template, direct it to the documented `/auth/confirm?token_hash=...&type=...`
   route and make sure recovery links route to `/reset-password`.

## Manual test plan

Use a test account, not a real driver's account.

### Registration + confirmation
- Submit a valid name/email/password (at least 8 characters).
- Verify invalid email and short password are blocked by the browser.
- With email confirmation enabled, verify the page says a confirmation may
  have been sent, does not disclose whether an account already exists, and
  permits resending a confirmation.
- Open the newest email. Confirm it lands on `/app/dashboard` with a valid
  session. Older/expired links should return to `/login` with clear guidance.
- Test confirmation URLs generated by Production; do not test production
  auth using an un-allowlisted Vercel deployment URL.

### Login + protected routes
- Valid credentials open the requested safe internal `next` route.
- Wrong password shows generic helpful guidance without exposing provider
  internals.
- Unconfirmed email shows confirmation guidance and a resend action.
- Opening `/app/dashboard` signed out sends the browser to login.
- Missing/malformed Supabase config in Production does NOT open demo mode.
- A `next=https://attacker.example`, `next=//attacker.example`, or a
  backslash redirect must fall back to `/app/dashboard`.

### Password reset
- Request a reset for an address. The UI should not reveal whether the
  address has an account.
- Open the newest email and reach `/reset-password`.
- A missing/expired session cannot change the password.
- Mismatched/short passwords are blocked. Valid new password updates, clears
  the recovery session and returns to login with a success message.
- Sign in with the new password, and verify the old password fails.

### Session and mobile checks
- Test Safari, Chrome, an incognito/private window and a fresh browser profile.
- Test on a phone using the canonical HTTPS domain.
- Confirm redirects preserve Supabase cookie rotations and that auth responses
  aren't cached.
- Confirm service-worker caches never store login/signup/recovery/callback pages.
- Check Supabase email delivery and rate limits if repeated requests fail.

## Known boundaries

- Code cannot add the production URL to Supabase Auth's Redirect URL allowlist
  from the website repository. That must be verified in the Supabase project.
- Email delivery itself depends on Supabase/SMTP configuration and provider
  rate limits; successful API response means accepted, not guaranteed inbox
  delivery.
- No user credentials, confirmation tokens, reset tokens, or session cookies
  should be written into application logs or support tickets.
